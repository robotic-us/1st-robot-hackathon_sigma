# CLAUDE.md

SIGMA — an infant-responsive robotic cradle (research prototype, Robot
Hackathon 2026, KAIST). The motion behaviour is a transcription of
`docs/infant_robotic_cradle_evidence_report_ko.pdf` (Korean): a 50-motion
library (M01–M50), a kinematic envelope, and a safety-first state machine.
That PDF is the spec — when motion behaviour is in question, it wins.
Architecture and the report↔code traceability table: `docs/ARCHITECTURE.md`.

## Layout

- `serve.py` — the entry point: sensing → CradleMachine → MotionEngine → SSE/MJPEG dashboard (`web/`: `index.html` markup + `style.css` + `app.js` + `fonts/` (self-hosted IBM Plex — the demo LAN has no font CDN), no build step; `serve.py::STATIC` is the whole served whitelist). Card-based clinical-monitor UI: "now" cards, the emotion-process timeline (seeded from `/history`, 1 Hz × 15 min), decision feed + learned preferences (when `--policy`), camera/controls/log, library + internals drawers. 2D only; 3D lives in RViz.
- `core/` — `cradle.py` (M01–M50 library + MotionEngine + CradleMachine — the heart), `policy.py` (the IDEA.md soothing policy: happiness ranks; the brains `ReflexBrain`/`DreamBrain`/`OllamaBrain`/`ClaudeBrain`; `WorldModel` (this infant's taste, wear and transitions) + `ChunkMatcher` (dreams every candidate forward, docs/dream-chunk.md); `SoothePolicy` — wired in as `CradleMachine.advisor`, which only ever *suggests* the motion a trial uses; the machine validates every pick and keeps all safety decisions), `pvector.py` (P-Vector world model; the m50 suite round-trips the compiled CSVs through it), `phorce_iface.py` (only file that knows phorce/ROS 2; also `SlotBridge`, the decisions→slots replayer).
- `perception/` — `nubzuki.py` (**the vision system**: names a Nubzuki pose by matching the figure against 102 reference crops, puts it on the sheet's circumplex, and maps it into the cradle's five states. Abstains rather than guesses when the frame is too degraded. It reads the *iPad*, never an infant. Graded against `docs/Nubzuki.jpg` by `tests.py::nubzuki`; `tools/nubzuki_wheel.py` draws the grade), `baby.py` (the virtual infant), `listen.py` (mic → distress; **orphaned** since the 2026-08-08 removal — nothing calls it, `tests.py::listen` still covers it).
- `apps/` — `animate.py` (RViz player: `--tour`/`--motion` replay the library through `MotionEngine`).
- `core/rig.py` — **the measured five-bar kinematics + RosSide**; the one home of the geometry convention (was `apps/demo.py`).
- `webapp/` — the dashboard as a Next.js app, a *client* of `serve.py` and not a replacement: the `web/` trio is still what the server serves and what `tests.py` checks. Needs a Node toolchain this repo does not ship; see `webapp/README.md`.
- `tools/` — one-off generators: `make_motions.py`, `make_urdf.py`, `nubzuki_wheel.py`; plus `aim_camera.py`, which is a setup aid rather than a generator (`tests.py::nubzuki` covers its two judgements; the camera half cannot be tested there).
- Data: `motions_m50/` (the 50-slot library), `motions_n34/`, `cad/`, `data/` (generated figures; `data/bench/` is where `--dump` puts captured camera frames). *(Legacy removed 2026-08: the whole infant-vision stack and its data — `models/`, `faces/`, `bench/`; `motions/`, `tags/`, `slots.json`, `perception/tag.py`, `core/dream.py`, `core/slot_table.py`, `apps/{demo,care,run}.py`, `tools/enroll.py`, `--dream-auto`, `/slots`, `/play` — the DREAM/tag stack. `core/pvector.py` stays: the m50 suite round-trips the compiled CSVs through it.)*

## Conventions

- **Run everything from the repo root** — data paths (`motions_m50/`, `cad/`, `web/`) resolve from cwd. Scripts in subdirs still run directly thanks to a `sys.path` bootstrap block at the top of each.
- **Tests live only in `tests.py`** — modules carry no selftests and no `--selftest` flags. New behaviour → new/extended suite there, registered in `SUITES`.
- Time is injected everywhere in `core/cradle.py` (no `time.time()` inside) so the machine is testable with a fake clock. Keep it that way.
- Module docstrings follow a house style: what it is, why it exists, run lines. Match it.

## Hard-won facts (do not rediscover)

- **OpenCV is 4.5.4** on this Jetson. It has no DNN face stack any more (removed 2026-08-08), but the version still constrains anything new: check a model parses *and runs* under 4.5.4 before depending on it.
- **pcm MotionMap rules**: MS ID inside the CSV must match the filename number; `MD ID` is 1-based; P-Vector cell = `"yd_deg, L_traj_ms(1 kHz), s0, sd"` with `yd` an *absolute* target in degrees; slot ids capped at `MAX_MOTION_ID = 50`.
- **Lever arm**: `PIVOT[2] - AXIS0[2]` (≈227 mm) → 1° ≈ 4 mm of sway is the *aggregate* gain, and it is still the right number for a back-of-envelope check. It is not a per-crank conversion — see the five-bar facts below. Constants live in `core/rig.py`, printed by `make_urdf.py` on every rebuild.
- **R-grade motions** (M29–M50) are research-only: engine refuses them without `--research`; never route them into automatic behaviour.
- **The N system (N01–N34, grade N)** lives beside the report library in `core/cradle.py` (`N_LIBRARY`, kind `npath`, shapes in the ML–Z plane, envelope-gated at import like everything else). It is the policy's whole search space (`N_CANDIDATES`, 26 sustained entries — no N01, no decay variants); the baby's `Personality` has *feature-level* tastes (shape/size/speed/vibe + mood interplay) on top of id-level love/hate, and `ReflexBrain` generalises over the same features and never lets one motion monopolise a fussing baby (`MAX_RUN`).
- **The rig is two five-bar linkages, not a parallelogram rocker.** Measured off `docs/udrf_assembly.stl` (contact graph + IK), not assumed. Every leg is a *two-link chain* — `axis_N` → `lower_N` (crank, 152 mm) → knee → `upper_N` (rod, 152 mm) → platform — and all four legs are the same part. Legs 0 and 1 share one base pivot and meet at **one** platform point with mirrored elbows (+35.6°/−47.0°); legs 2 and 3 likewise. Two cranks, two rods, one shared endpoint = a closed five-bar, 2 DOF per pair. The passive knee absorbs the reach change a rigid parallelogram could not.
- **Three channels, and Z is real.** `sway` (all four cranks the same way) → horizontal, **4.17 mm/deg**. `heave` (each pair's two cranks *opposed*) → **vertical, 3.02 mm/deg**. `pitch` (pair against pair) → see-saw. Cross-checked: sway A10 solves to 2.40° against the report's documented 2.53°. The old "Z modes can't play / no vertical DOF" claim was wrong — M48–M50 now compile to real motion.
- **The assembly STL is not finished, so do not read the rest pose off it.** The top four bearings are not yet mated to the table: the platform is only resting in place, the two pairs sit at unequal reach (228.3 vs 262.0 mm) and the table is tilted 9.7° — confirmed twice over, by its deck normal `(-0.17, 0, 0.99)` and by the line through its mounts. Taking `REST_A`/`REST_B` from the export baked that tilt into every motion. What the export *does* pin down (because it does not depend on the arms) is that the table is rigid with coplanar mounts 200.4/199.6 mm apart, matching the 200.0 mm base-pivot separation — so the neutral pose is the symmetric one: equal reach, each endpoint above its own base, table level, cranks at ±36.43°. `RIDE_MM = 245.2` (the mean of the two observed reaches) sets where in the travel that sits and is **the one number still worth measuring on the finished rig**.
- **AP does not exist as a translation.** Every joint turns about Y, so all motion is in the XZ plane; there is no second horizontal axis. The report's 11 AP entries are rendered as **pitch** (`AP_AS_PITCH` in `core/rig.py`) — a deliberate substitution, not the report's motion.
- **`core/rig.py::axis_angles()` / `cradle_angles()` is the one definition.** It solves the real five-bar IK (reproduces the CAD's own crank angles to 0.6°). The compiler, `serve.py`'s RViz mirror and `apps/animate.py` all go through it; `tests.py::m50` and `::animate` assert both the CSVs and the live path. Fixing only one of the three silently collapses everything back into the same sway — that has now happened twice.
- **The linkage is nonlinear, so bounds need both directions.** At the level neutral the two pairs are identical and 10 mm of sway costs [2.27, 2.40, 2.27, 2.40]° — but the cranks still differ within a pair, −20 mm costs more crank angle than +20 mm, and pitch/heave cost more per millimetre than sway (3.02 vs 4.17 mm/deg). Any ceiling computed from sway alone, or from one sign, under-counts; `tests.py::animate` derives its ceiling over every channel and both signs for exactly this reason.
- **Every upper arm joins the holder; the tree is re-rooted to make that true.** A URDF is a tree, so the holder can have only one parent — but all four arms carry it in hardware, and a model where three join nothing is not the machine. Leg 0 runs *up* to the holder and legs 1–3 hang *down* from it: `base_link → axis_0 → lower_0 → upper_0 → platform → upper_{1,2,3} → lower_{1,2,3} → axis_{1,2,3}`. The knees are real joints too (`joint_knee_N`), not welds. The open end is therefore at the actuators — and they are bolted down, so **closure means each actuator lands back on its own pivot**: `tests.py::animate` walks the published joints through the real URDF exactly as `robot_state_publisher` does and asserts this (worst 0.025 mm across all channels).
- **`joint_state()`'s first four entries are NOT the four cranks.** The order is `axis_0, knee_0, platform, bearing_1, knee_1, bearing_2, knee_2, bearing_3, knee_3` — it interleaves, because each leg hangs off a different parent. Use `cradle_cranks()` for anything measuring amplitude; `library_angles(..., solve=)` picks which. Indexing `[:4]` for "the cranks" is wrong and reads as a wildly wrong amplitude. **`core/rig.py::JOINT_NAMES` is the only joint-name list** — both publishers (`RosSide`, `apps/animate.py`) reference it, never a copy; a stale copy is how RViz broke after the re-root (nonexistent `joint_axis_1/2/3` published, real `joint_bearing_1/2/3` never published, three arms with no TF). `tests.py::animate` asserts the list matches the URDF's revolute joints and that both publishers share the one object.
- **Angles are measured from +Z toward +X, everywhere, via `_ang()`.** Writing the holder's tilt the natural way (`atan2(Δz, Δx)`, from +X) flips its sign against the joint convention — the holder then rotates the wrong way and *doubles* its tilt instead of levelling, which put the far actuators 68 mm off their pivots. One convention or nothing lines up.
- **Solve each leg against its own mount, with its own link lengths.** The holder's four mounts sit a few mm apart, and the legs measure 151.7–152.5 (crank) / 151.9–153.4 (rod). Treating each pair as sharing one endpoint, or using one rounded length for all four, each cost about a millimetre of closure error.
- **`--viz-gain` multiplies plate travel, not joint angles.** The linkage is nonlinear, so scaling the angles produces a pose the mechanism cannot reach and lifts the rods off their bearings. `cradle_joint_state(..., gain=)` scales the travel and re-solves, so the exaggerated pose is a real pose. At gain 5 the worst joint reaches 39.6°, well inside the ±90° limit.
- **`./sim.sh` does not move anything.** The phorce sim backend announces itself in `/tmp/sigma-sim.log` as a `mechanism-neutral fake PCM ... 로봇은 움직이지 않습니다 (aggregate 실행 800ms)`: it validates MS IDs, request tokens and completion semantics, then returns SUCCEEDED after a fixed ~0.8 s without walking the P-Vector chain. Measured — a 9-segment slot and a 128-segment 120 s taper both take 0.78 s, and `pvector_index` never leaves 255. Never use it to judge a trajectory; use RViz (`cad/view.sh` + `apps/animate.py --tour`).
- **Vision is capped in the fuss band, and that survived the removal.** `perception/nubzuki.py::distress_of` puts a visual DISTRESS_FACE in [0.30, 0.42] < CRY_LEVEL 0.45, so the ladder — which only climbs at `ema >= CRY_LEVEL` — never opens on vision alone. Note the two levels a sighting carries: `recovered_level` is the number the machine *sent* (an echo, for checking the loop) and can be 1.0; `asserted_level` is what a visual reading may *claim* and never exceeds 0.42. Conflating them hands the escalation ladder to a cartoon — `tests.py::nubzuki` asserts the ceiling. UNKNOWN means no figure, which drops `present` to the safety gate.
- **The mascot recognizer names poses by nearest reference crop, not by rules — and the rules' death is the lesson.** A hand-written ladder (red head = rage, brown legs = poorly) scored **17/17 on the sticker sheet it was written against and 7/17 on `docs/poses/`**, the renderings `web/baby.js` actually produces and the camera actually sees. Retuning reached 11/17 and stalled: the marks that separate the rest — tears *under* the eyes, spectacles *around* them, a bow *on top* — are positions on a face, and a colour fraction over the whole figure has already discarded that. Template matching gets **17/17 on both**, including through a full camera simulation (8° rotation, perspective, glare, blur, noise, JPEG q45), and **abstains instead of guessing** on frames degraded past reading. Don't reintroduce per-pose colour rules; if a pose is wrong, add or re-bake its reference crop. Colour still decides *segmentation* and `is_nubzuki()`, which it does well.
- **Detecting Nubzuki on a real panel is a separate problem from naming it, and it is the harder one.** Naming was 17/17 while detection on a photographed screen was ~2/17 — "the classifier works, it just never finds him". Cause: every threshold was written for renders, where the page is pure white and the paint fully saturated. Photographed, the body blue arrives at **S≈30 against the S>55 the mask asks for**, so the paint vanishes and only the ink outline survives. The pipeline is therefore **page → normalise → mask**, in that order: `find_page()` on the *raw* frame (bright, near-neutral, largest), then `normalise()` white-balances and restores saturation *within it*. Order is not cosmetic — normalising the whole room lifts grey walls into the mask and merged an entire 1280×720 frame into one blob. Two traps already paid for: the saturation gain is clamped **≥ 1.0** (allowed to cut, it damped the vivid sheet 6% and re-split the angry pose's flush bridge), and the blob floor is a **fraction of frame area**, not 6000 px. Simulated panel photos: 2/17 → 12/17 detected, zero wrong. Use `--debug` to see page/mask/gate separately — "it sees nothing" is three different bugs.
- **Distance is a template problem, not a detection problem.** "It does not catch when it is too far" measured as: *detection* held 17/17 all the way down, *naming* collapsed (8/17 at a 128 px figure, 0/17 at 52 px) and it abstained rather than guessed. A figure 60 px tall is not a shrunken 600 px one — coarser mask, softer edges — so it lands past MAX_DISTANCE from a full-resolution template. Fix: bake every reference at five sizes (`SCALES` in `tools/make_nubzuki_templates.py`, 102 crops), plus anchor `find_page` at the **99.5th** brightness percentile instead of the 90th — with a distant panel most of the frame is room, so the 90th percentile sits on the furniture and the grey desk wins the page. Named-correct by figure height: 128 px 8→17, 72 px 1→13, 52 px 0→11. Re-bake after touching either.
- **Point the camera with `serve.py --sense --crop x,y,w,h`, and know which of the two problems you are solving.** The crop (fractions when all ≤ 1, else pixels; `parse_crop`/`crop_frame`/`centre_region`/`magnify` live in `perception/nubzuki.py` and are imported by `serve.py` — **one definition, because both readers must frame identically**, and `tests.py::serve` asserts the objects are shared. `nubzuki.py --camera/--video` takes the same two flags. Applied to the raw frame before anything reads it, so the recognizer, the overlay, the votes and the `--dump` corpus are all about the same pixels) settles the **page competition**: `find_page` takes the largest bright near-neutral region, so any lit whiteboard or window larger than the iPad wins and the mascot is never looked at. Measured on a synthetic dim nursery with one lit whiteboard: **0/17 named on the full frame, 15/17 cropped to the panel.** What it does *not* buy is resolution — a distant figure is still the template problem above. Second trap found in the same measurement: whenever the surround is **darker** than the page (an iPad bezel, a dim room), the ink mask keeps the *ring* around the page, it passes `is_nubzuki`, gets confidently named, and at ~4× Nubzuki's area it wins the largest-figure rule outright. `serve.py::mascot_reading` therefore skips any figure that **encloses** another — a frame is not a mascot; `tests.py::serve` asserts it.
- **Digital zoom pays, but only in the regime where naming was already failing, and it is not free.** `serve.py --sense --zoom N` (`magnify`; bare `--zoom` reads the middle 1/N via `centre_region`, which keeps the pixel count flat) creates no detail, and `classify` resizes every figure to CROP_N anyway — so "no effect" was the honest expectation and it is wrong. The steps *before* the classifier (mask morphology, `square_crop`'s 6 px pad, `_silhouette`) are written in fixed pixels, and a small figure starves them. Named-correct on a photographed panel (warp, glare, blur, noise, JPEG q45), already cropped to the panel, three seeds: 44 px figure **8–10/17 → 14–15/17 (×2) → 16/17 (×3)**; 53 px **12–14 → 16–17**; **63 px and above, all three within noise**. **Zoom is a band, not a dial: above the band it actively breaks naming, and that was measured on the real rig.** On a live 1280×960 frame of the phone in the cradle (figure 173 px) every zoom lost the figure — ×1.5, ×2 and ×3, bare or on a crop, and unchanged by interpolation (cubic/linear/nearest) or by blurring before or after, so it is neither aliasing nor noise. Traced through the pipeline: the figure is still found and still passes `is_nubzuki`, but magnifying widens the interpolated outline, the paint fraction falls (`blue` 0.67 → 0.46) and the template match drifts past its ceiling (28.5 → 40.2, `classify` returns None: *"nothing within reach"*). It abstains rather than guessing, exactly as designed. Sweeping the same figure across scales, naming held from **~60 px to ~173 px and failed on both sides**. So `--zoom` is for a *distant* panel (44–60 px), and pointing it at an already-large figure is how you turn a working reading into UNKNOWN. Check the figure height before reaching for it — `tools/aim_camera.py` prints it.
- **`/baby` tints its own page, so the recognizer's white-page assumption only survives because the room is in shot.** `web/baby.js` paints a mood-coloured radial wash over the white body (blue calm, red rage, purple dusk, pink flush, orange rainbow) — on camera the screen reads pink at S≈46, not white. Uncropped this is harmless: `find_page` anchors on the neutral desk and white-balances against *that*. Crop tight to the screen and the wash becomes the page, `normalise` white-balances against a coloured surface and lifts the wash into the mask, merging the whole screen into one blob that cannot be named (measured: phone-body and screen-only crops both named **nothing** where the full frame named correctly). So on this rig **cropping to the panel is wrong** — the opposite of the distant-panel case above. Crop only to a box that is mostly figure, or not at all.
- **The cost is not a constant, and it lines up with the benefit** — it scales with the *magnified* area, so ×3 is cheap exactly where it helps. Per frame through `nz.read` on this Jetson, by crop size: an 82×100 crop runs 10/18/28 ms at ×1/×2/×3 (35 fps at ×3), 200×250 runs 24/57/153 ms, 340×400 runs 52/165/340 ms, 500×620 runs 89/349/766 ms. A figure small enough to need ×3 arrives inside a small crop, so ×3 costs tens of milliseconds; ×3 on a big crop is what costs half a second, and there it measured no better than ×1. `tools/aim_camera.py` times all three on your actual crop rather than quoting these. Order to reach for: **`--camera-size` (real detail) → `--crop` (the page competition) → the zoom the timing table justifies → move the camera closer**.
- **A frame is a vote, not an answer — and only the pose is voted, never presence.** `serve.py --sense` reports the **most-shown pose of the last `--vote` seconds** (default 3.0, `nz.Tracker`, `0` disables) because at a blend midpoint the drawn face genuinely sits between two poses and consecutive frames round either way, which reaches the dashboard as flicker. `serve.py` keeps the newest sighting per pose so the winning vote turns back into a reading with its own label and level. **Presence is deliberately excluded from the vote**: it stays on the 2 s `SIGHT_GRACE_S` hold, so a figure that truly leaves still reaches the 0.7 s safety gate on time instead of being asserted for another window. `tests.py::serve` asserts both halves — flicker suppressed, a settled new pose still takes over as old votes age out, and no vote can manufacture presence.
- **The camera overlay is sized to the frame, because a crop makes the frame small.** `nz.overlay_scale` scales the boxes and labels by `width/640` (clamped 0.35–1.6). A 160×144 crop drawn with the fixed 0.62 font produced lettering that covered the figure it labelled, and the dashboard upscaled it further — which reads as "the labels were drawn before the crop". They were not: the status line sits at `(16, 30)`, which a crop starting at x=237 would have excluded entirely. The panel shows the recognizer's own frame on purpose, so the overlay has to follow the frame's size.
- **Report-spec judge rules (sections 4.2–5)**: cry is decided by **duty cycle + vocal-unit length**, never loudness alone (§4.2's own warning); a closure <1 s is a blink; closure within 2 s of a vocalisation is never sleep; SLEEP_TENTATIVE = 10 s closed+quiet, SLEEP_STABLE adds 60 s low body flow; improving/worsening = 2 of the *observable* signals over 30 s. `CRY` maps ≥ CRY_LEVEL because audio confirmed it. Pain/posture → `Reading.alarm`, which rides the machine's fault input (same path as a jam) — interrupt and call, never soothe.

What went with it: the report's §4.2 duty/unit cry test, the §4.3 sleep ladder, FER+ expression, BlazePose posture. The five-state vocabulary was **kept** and re-homed into `nubzuki.py` because the decision layer is built on it. `serve.py --verify` no longer judges anything — its phases assert their own state, so it tests the machine, not a recognizer. Everything is recoverable from git history if the report path is ever needed again.
- **Policy credit is engagement-gated** (`core/policy.py::SoothePolicy.observe`): a step's outcome is the rank last seen while its motion played at strength (env > 0.2, not tapering), settled when the engine parks. Crediting the *best* rank while merely `engine.active` let natural recovery during tapers and ramps credit the motion — the first learn_report run had the policy exploiting a motion the baby hated. `tests.py::policy` asserts hated motions never score positive.
- **DREAM-Chunk has two halves and only the matcher pays — measured, don't re-litigate it blind** (`docs/dream-chunk.md` carries the tables). The **matcher** (`core/policy.py::ChunkMatcher`/`DreamBrain`, `--policy dream`) dreams all 26 candidates forward through a learned comfort model and takes the best: **−26.4 % upset / −57.1 % crying vs the ladder, and −6.8 % / −18.2 % vs the reflex heuristic** (40 paired nights; the vs-ladder figures are t=−8.5/−9.0, the vs-reflex margin only t=−1.8/−1.9 — quote it as a direction). Its ranking is inspectable live — `policy.plan` in `/events` feeds the dashboard's *What it dreamed* card. The **monitor** half (a divergence tube driving early switches) detected well but measured **+2.9 % upset** end-to-end, so it was **deleted** — flag, hook and tube — rather than kept as a switched-off option through the safety machine.
- **The planner's estimator was audited against the infant's hidden taste, and needed all of it.** Three defects (credit as a ratio of a small `y0`, habituation written into taste, a veto that exiled 21 of 26 motions) plus a sample-size wall: per-id taste correlated **+0.03** with the truth, feature-pooled **+0.44**, hierarchical (id shrunk by n/(n+40)) **+0.60**. Fixing them *alone* made things worse — −23.7 % → −6.6 % vs the ladder — because the old advantage was **forced rotation** from noisy estimates, not personalisation (reflex gets −21 % on `MAX_RUN` rotation alone; repeat-rate tracks performance across every arm). Adding a UCB confidence bound `c·sqrt(ln N/n)` restored the rotation for the right reason: **−26.4 %**. Don't remove the bound without re-measuring.
- **A world model only pays against a plant with memory.** On the *original* memoryless baby the planner tied the reflex heuristic exactly (−0.0 %, t=−0.01): P(no step-down in 7 s) ≈ 0.57 even for a working motion, so there was nothing to predict. `VirtualBaby(cumulative=True)` (now the default) integrates soothing into a 0..1 settling score and shows partial progress in the level; `cumulative=False` keeps the old dynamics so the comparison is reproducible. The change was justified on realism, not on results: it made the *ladder* baseline worse (18.6 → 20.4 upset min/night) and left the reflex margin unchanged — only the planner improved. Note this if anyone asks whether the sim was tuned until the method won.
